# Ubiquitous language

## Interview and build

- Consult the glossary at the start of any discussion that defines terms, and treat terms settled there as candidates to add. When a term causes confusion, compare concrete scenarios and edge cases, then update the glossary so no two terms collide.

## Design and build

- Within a boundary, give each term one agreed meaning. Keep it in a shared glossary and use it the same way from requirements through code.
- In shipped tooling, use each consumer's own word for a concept (its tracker's term for a work item) rather than imposing yours.
- When absorbing an outside source, keep a running glossary that maps each of its terms to your term and to what research says, instead of adopting its names.

## Build

- Keep the glossary lean: only terms that remove ambiguity, with no globally understood concepts and no implementation details.
